# Androidテスト結果台帳 要件定義（初版）

## 1. 目的

現在Excelで管理しているAndroidアプリの機能テストを、手動テストと自動テスト（Maestro）の両方について記録・閲覧できるローカルWebアプリに置き換える。

テスト結果、スクリーンショット、実行時の詳細情報をテスト対象アプリごとに管理し、直近の結果比較や過去履歴の確認を容易にする。AIからも誤りにくい形式で結果を登録できるようにする。

## 2. 想定構成

- バックエンド: Go + Echo
- フロントエンド: React
- データベース: PostgreSQL
- 起動・実行環境: Docker Composeなどのコンテナ構成
- 利用形態: ローカル環境で利用
- 画像: ローカル永続ストレージに保存し、DBには参照情報を保存

## 3. 対象範囲

### 対象

- テスト対象アプリ単位でのテスト管理
- 手動テストおよび自動テスト結果の記録
- テスト結果・スクリーンショット・実行時情報の閲覧
- 過去のテスト結果の比較
- テストケースと結果の編集
- 編集履歴の保存
- Maestroの実行結果との連携（実行方法の調査後に具体化）
- 現行Excelから必要なデータを整理し、初期データとして移行

### 初版では対象外

- Maestro実行端末やエミュレーターの管理・起動
- ダッシュボードからのMaestro実行オーケストレーション
- AIによる自動合否判定
- 複雑な分析・レポート機能
- 外部公開やクラウド運用

## 4. 機能要件

### 4.1 アプリ単位の管理

- すべてのテストケース、実行回、結果をテスト対象アプリに紐づける。
- アプリを選択すると、そのアプリのテスト項目と実行履歴を確認できる。

### 4.2 テストケース管理

- アプリごとのテスト一覧を表示する。
- テストケースを追加・編集できる。
- テストケースには、少なくとも名称と手順・期待結果を記録できる。
- テストケースの編集によって、既存のテスト実行結果が書き換わらないようにする。

### 4.3 テスト結果の記録

- 手動テスト結果を画面から登録・編集できる。
- Maestroなどの自動テスト結果を登録できる方法を用意する。
- 結果は少なくとも「未実施」「成功」「失敗」「保留」を区別する。
- テスト方法（手動／自動）を記録する。
- 実行日時を記録する。
- テスト時の詳細情報を記録できる。対象情報はExcelの棚卸し後に確定する。
- 失敗時のコメントや実際の結果を記録できる。

### 4.4 スクリーンショット・添付ファイル

- テスト結果に写真・スクリーンショットを添付できる。
- 実行後に写真をアップロードできる。
- 結果詳細画面から添付画像を閲覧できる。
- 画像はテスト結果との紐づけを保持し、DBにはファイル参照情報を記録する。
- Maestroが出力するスクリーンショットを登録できるようにする。

### 4.5 履歴・直近結果の表示

- テストケースごとに過去の実行結果を確認できる。
- 同じテストケースの直近2回の結果を並べて表示する。
- 成功・失敗・未実施・保留を一覧上で識別しやすく表示する。
- テストケースの追加・編集と、各回の実行結果の履歴を分けて保持する。

### 4.6 編集履歴・誤編集からの復元

- 過去のテスト結果を修正できる。
- 修正前の状態を履歴として保存する。
- 少なくとも変更日時、変更前の値、変更後の値を確認できる。
- 誤編集時に過去の状態を確認し、手動で復元できる。
- 可能であれば変更者も記録する。利用者認証の要否は運用形態に応じて決める。
- 添付画像の置き換え・削除についても、過去状態を保持するかExcel棚卸し後に決める。

### 4.7 検索・絞り込み

- アプリ単位でテスト結果を表示する。
- 結果（成功・失敗・未実施・保留）、テスト方法、実行日などで絞り込める。
- 必要な絞り込み項目はExcel棚卸し後に確定する。

### 4.8 データ移行・出力

- 現行Excelの内容を確認し、必要な項目をDBへ移行する。
- Excelの全項目をそのまま再現せず、利用実態に合わせて簡素化する。
- Excelへの出力は必要性を確認してから実装する。

## 5. AI連携

- AIがDBを直接更新するのではなく、入力項目と値を限定したAPIを通じて結果を登録する。
- APIはテストケースID、結果、コメント、実行時情報、添付画像の参照などを構造化して受け取る。
- MCPの導入は必須要件とせず、APIの形が固まった後に必要性を判断する。

## 6. Maestro連携に関する調査事項

Maestroの実利用は未検証のため、実装前に最小のPoCを行う。

- 対象端末またはエミュレーターでテストフローを1本実行する。
- 実行コマンド、成功・失敗の判定方法、終了コードを確認する。
- テスト結果レポートの形式と保存先を確認する。
- `takeScreenshot`で取得したPNGの保存場所を確認する。
- ログ・レポート・スクリーンショットとテストケースを対応づける方法を確認する。
- Maestroの実行は初版では既存の手順で行い、台帳側は結果の取り込み・登録に限定する。

## 7. Excel棚卸し事項

- シート、列、入力規則、代表的な記入例を洗い出す。
- 現在記録されているテスト時の詳細情報を確認する。
- 重複・未使用・自由記述の項目を識別する。
- テストケース、実行回、実行結果、添付資料に整理する。
- 初版で残す項目と廃止する項目を決める。
- 移行対象データの範囲と移行方法を決める。

## 8. 非機能要件

- コンテナ環境からローカルで起動できる。
- PostgreSQLのデータと画像ファイルは、コンテナ再作成後も保持される。
- DBと画像ファイルをバックアップ・復元できる方法を用意する。
- ローカル利用に必要な範囲で、画面とAPIを保護する。認証要否は利用者数・端末共有の有無を踏まえて決める。

## 9. 未決事項

- Maestroをどの端末・実行環境で動かすか。
- Maestroの出力をAPIへ取り込む具体的な方法。
- Excelから移行する項目・過去データの範囲。
- テスト時の詳細情報の具体的な項目。
- 画像の編集履歴・削除・保持期間。
- 利用者認証と変更者の識別方法。
- Excel出力の必要性。
- テスト結果の訂正理由を必須にするか。

## 10. 初期の進め方

1. 現行Excelを棚卸しする。
2. Maestroでサンプルフローを1本実行し、レポートとスクリーンショットの出力を確認する。
3. 2つの調査結果をもとに、初版のDB項目と画面を確定する。
4. Go + Echo、React、PostgreSQLのコンテナ構成で最小版を作る。
5. 手動入力、Maestro結果の登録、過去履歴・編集履歴の確認を行う。

## 11. 基本設計（初版）

### 11.1 データの考え方

- すべてのテスト情報はテスト対象アプリを起点に管理する。
- テストケースは再利用する定義、テスト実行は特定の日時・環境で行った1回分、テスト結果はその実行内の各テストケースの結果として扱う。
- テストケースの編集・無効化によって、既存の実行結果を変更しない。
- 結果の誤編集に備え、編集履歴は現在値と別に保存する。
- テストケースの実行時点の内容も確認できるよう、結果作成時にケース名・手順・期待結果のスナップショットを保持する。
- テスト項目の手順は単一テキストとして扱う。
- テスト項目にはカテゴリを1つ設定する。初版ではカテゴリ専用テーブルを作らず、アプリ内で使うカテゴリ名をテキストとして保持する。

### 11.2 画面構成

- **アプリ選択／概要**: アプリを選択し、最新の成功・失敗状況と最近の実行を確認する。
- **テスト一覧**: 選択アプリのテスト項目、直近2回の結果、状態を一覧する。
- **テスト項目編集**: テスト項目を追加・編集・無効化する。無効化した項目は新しい実行対象から外すが、過去結果からは削除しない。
- **実行詳細**: 実行者、日時、アプリ版、端末・OS、実行方法および各ケースの結果・添付を確認する。
- **結果編集**: 手動結果の登録・修正、コメント、実際の結果、写真のアップロードを行う。
- **編集履歴**: 変更前後の値を確認し、必要に応じて過去状態を復元する。

### 11.3 1回のテスト実行

テスト実行は1つのアプリに対する1回のテストセッションを表す。1回の実行に複数のテスト結果を含める。

- 手動実行と自動実行を同じ実行モデルで記録し、実行方法で区別する。
- 実行時点で選択したテストケースを実行結果として作成する。
- 直近2回の比較は、同一テストケースの実行結果を実行日時の降順で取得して表示する。
- テストケースを後から追加しても過去の実行に遡って追加しない。

## 12. DB設計（論理設計）

初版は以下の6テーブルを基本とする。列の型・制約・インデックスはExcel棚卸しとMaestro PoC後に物理設計で確定する。

### 12.1 `apps` — テスト対象アプリ

- `id` (PK)
- `name`
- `package_name`（任意）
- `description`（任意）
- `created_at`, `updated_at`
- `is_active`

### 12.2 `test_cases` — テスト項目

- `id` (PK)
- `app_id` (FK → `apps.id`)
- `case_key`（アプリ内で一意な識別子）
- `category`（カテゴリ名）
- `title`
- `precondition`（任意）
- `steps`（複数手順を含められる単一テキスト）
- `expected_result`
- `test_type`（manual / automated / both）
- `sort_order`
- `created_at`, `updated_at`
- `is_active`（削除ではなく無効化に使用）

テスト項目の増減は、このテーブルのレコード追加・編集・無効化で行う。項目ごとにDBスキーマを変える動的フィールド方式は初版では採用しない。

### 12.3 `test_runs` — テスト実行環境・実行回

- `id` (PK)
- `app_id` (FK → `apps.id`)
- `run_type`（manual / automated）
- `runner_name`（例: Maestro。任意）
- `executed_by`（認証を導入しない場合は自由記述またはNULL）
- `started_at`, `finished_at`
- `app_version`
- `device_name`, `android_version`（任意）
- `notes`（任意の補足情報。追加の実行環境項目はExcel棚卸し後に必要な列だけ追加する）
- `summary`, `created_at`

「誰が・いつ・どのアプリ版・どの端末／OSで実行したか」を記録する。

### 12.4 `test_results` — テスト結果履歴

- `id` (PK)
- `test_run_id` (FK → `test_runs.id`)
- `test_case_id` (FK → `test_cases.id`)
- `status`（not_run / passed / failed / blocked）
- `actual_result`（任意）
- `comment`（任意）
- `case_snapshot`（実行時点のカテゴリ・ケース名・手順・期待結果を保存するJSONB）
- `created_at`, `updated_at`

同一実行内で1ケース1結果となるよう、`(test_run_id, test_case_id)`に一意制約を設ける。後から結果を修正しても、通常は同じ結果レコードを更新し、更新前後を`edit_history`へ保存する。

### 12.5 `attachments` — 写真・スクリーンショット・ログ

- `id` (PK)
- `test_result_id` (FK → `test_results.id`)
- `file_name`
- `storage_path`
- `mime_type`
- `file_size_bytes`
- `uploaded_at`
- `uploaded_by`（任意）
- `caption`（任意）

ファイル本体はコンテナ外の永続化ボリュームに置き、DBには参照情報を保存する。後からのアップロードと、1結果への複数ファイル添付を可能にする。添付ファイル自体の編集世代は管理しない。

### 12.6 `edit_history` — 編集履歴

- `id` (PK)
- `test_case_id` (FK → `test_cases.id`, nullable)
- `test_result_id` (FK → `test_results.id`, nullable)
- `action`（created / updated / deactivated / restored）
- `before_data`（変更前JSON）
- `after_data`（変更後JSON）
- `changed_at`
- `changed_by`（任意。初版では自由記述とし、ログイン機能は設けない）
- `reason`（任意）

テスト項目またはテスト結果の変更前後を追記型で記録する。`test_case_id`と`test_result_id`のどちらか一方だけを設定する。添付ファイルの変更履歴は記録しない。復元時は過去行を書き換えず、復元操作を新しい履歴として追加する。

### 12.7 テーブル間の関係

```text
apps 1 ── * test_cases
apps 1 ── * test_runs
test_runs 1 ── * test_results
test_cases 1 ── * test_results
test_results 1 ── * attachments
test_cases 1 ── * edit_history
test_results 1 ── * edit_history
```

## 13. 未決の設計項目

- **Maestro実行**: 端末またはエミュレーター、実行コマンド、出力レポートとスクリーンショットの保存場所をPoCで確認する。
- **Excel移行**: 移行する列・過去データの範囲を棚卸しで決める。
- **実行環境情報**: 端末名・Android版・アプリ版など基本列を用意し、Excel棚卸し後に必要な項目だけ追加する。初版では自由形式JSONBを設けない。
- **変更者・実行者**: 初版ではログイン機能を設けず、必要な場合は名前を自由入力する。運用して認証が必要になったらユーザー管理を追加する。
- **編集理由**: 任意入力とする。初版では必須にしない。
- **添付ファイルの削除・保持**: 添付の世代履歴は持たない。削除やテスト項目無効化後の関連ファイルの扱いは、運用を見て後で決める。
- **Excel出力**: 必要性を確認してから追加する。
