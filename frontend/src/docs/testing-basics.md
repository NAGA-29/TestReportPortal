# テストの基礎知識

このページは、ソフトウェア開発における「テスト」の考え方を、初心者から中級者向けにまとめた読み物です。
テストの種類、テストケースの組み立て方、QAエンジニアの役割までを順に説明します。
用語に迷ったら、最後の「用語集」も参照してください。

## なぜテストをするのか

テストの目的は「バグをゼロにすること」ではありません。**リリースしてよいかを判断するための情報を集めること**です。

- **不具合を見つける** — 利用者に届く前に問題を発見します。
- **リスクを下げる** — 壊れると困る機能ほど重点的に確認します。
- **安心して変更できるようにする** — テストがあれば、修正やリファクタリングで既存機能を壊していないかを確かめられます。
- **品質を説明できるようにする** — 「何を、どこまで確認したか」を記録に残し、チームや関係者に共有します。

不具合は、見つかるのが遅いほど直すコストが大きくなります。要件の段階で気づけば文章を直すだけですが、リリース後に見つかると、修正・再テスト・再リリース・利用者対応まで必要になります。
そのため、開発の早い段階からテストを意識する考え方（**シフトレフト**）が重視されています。

### テストの7原則

国際的なテスト資格 ISTQB（日本では JSTQB）でも紹介されている、テストの基本原則です。

1. **テストは欠陥があることは示せるが、ないことは示せない** — テストに合格しても「バグがない」証明にはなりません。
2. **全数テストは不可能** — 入力の組み合わせは無限にあるため、リスクに応じて絞り込みます。
3. **早期テストで時間とコストを節約** — 早く見つけるほど安く直せます。
4. **欠陥は偏在する** — 不具合は特定の機能やモジュールに集中しがちです。
5. **殺虫剤のパラドックスに注意** — 同じテストを繰り返すだけでは、新しい不具合は見つかりにくくなります。
6. **テストは状況次第** — 銀行システムとゲームでは、適したテストのやり方が違います。
7. **「バグゼロ」の落とし穴** — 不具合がなくても、利用者の役に立たなければ品質が高いとは言えません。

## テストレベル

テストは、確認する範囲の大きさによって段階（レベル）に分けられます。小さい単位から順に積み上げるのが基本です。

| レベル | 確認する範囲 | 主な担当 | 例 |
|---|---|---|---|
| **単体テスト**（ユニットテスト） | 関数・クラスなど最小の部品 | 開発者 | 日付を整形する関数が正しい文字列を返すか |
| **結合テスト**（インテグレーションテスト） | 部品どうし、DBや外部APIとのつなぎ目 | 開発者・QA | APIを呼ぶと、DBに正しく保存されるか |
| **システムテスト** | アプリ全体を、利用者の操作どおりに | QA | ログインして商品を購入できるか |
| **受け入れテスト** | 業務やユーザーの要求を満たすか | 利用者・発注者・PO | 実際の業務の流れで使えるか |

### テストピラミッド

自動テストをどのレベルにどれだけ用意するかの目安として、**テストピラミッド**という考え方があります。

- **土台（多い）: 単体テスト** — 速く、安く、原因の特定もしやすい。数を多く書きます。
- **中段: 結合テスト** — 部品のつなぎ目を確認します。単体テストより遅く、準備も増えます。
- **頂点（少ない）: E2Eテスト（画面操作の通しテスト）** — 利用者に近い確認ができますが、遅く壊れやすいので、重要な流れに絞ります。

上が太い「アイスクリームコーン型」（手動テストやE2Eテストばかりで単体テストが少ない状態）になると、テストに時間がかかり、失敗時の原因調査も難しくなります。

## テストの種類

テストは「何を確かめるか」で大きく **機能テスト** と **非機能テスト** に分けられます。

### 機能テスト

仕様どおりに「動くか」を確かめるテストです。入力に対して期待した結果が返るか、画面遷移やデータの保存が正しいかを確認します。
例：正しいパスワードでログインできる、誤ったパスワードではエラーメッセージが出る。

### 非機能テスト

「どのくらい良く動くか」を確かめるテストです。機能テストに合格していても、ここで問題が見つかることはよくあります。

| 種類 | 確かめること | 例 |
|---|---|---|
| **性能テスト** | 応答時間や処理速度 | 一覧画面が2秒以内に表示されるか |
| **負荷テスト** | 多くの利用者が同時に使ったときの挙動 | 1,000人同時アクセスでもエラーにならないか |
| **ストレステスト** | 限界を超えたときの挙動と回復 | 高負荷で落ちた後、正しく復旧するか |
| **セキュリティテスト** | 不正な操作や攻撃への耐性 | 他人のデータを見られないか、SQLインジェクションが通らないか |
| **ユーザビリティテスト** | 使いやすさ、わかりやすさ | 初めての人が迷わず登録を完了できるか |
| **互換性テスト** | 端末・OS・ブラウザーの違い | Android 12 と 15、小型端末とタブレットで同じように動くか |
| **アクセシビリティテスト** | 障害のある人も使えるか | 読み上げ機能で操作できるか、文字を大きくしても崩れないか |
| **信頼性テスト** | 長時間・繰り返し使っても安定するか | 1日使い続けてもメモリが増え続けないか |

### 変更に関わるテスト

ソフトウェアは何度も修正されます。修正のたびに行うテストにも名前があります。

- **確認テスト（再テスト）** — 修正した不具合が、本当に直ったかを確かめます。
- **リグレッションテスト（回帰テスト）** — 修正の影響で、**今まで動いていた別の機能が壊れていないか**を確かめます。繰り返し実施するので、自動化の効果が最も出やすいテストです。
- **スモークテスト** — ビルド直後に、起動する・ログインできるなど最低限の動作だけを短時間で確認します。ここで失敗したら、詳しいテストに進まず差し戻します。
- **サニティテスト** — 特定の修正や機能に絞って、ざっと妥当性を確認します。

## ブラックボックスとホワイトボックス

テストの作り方は、中身（ソースコード）を見るかどうかで2つに分かれます。

- **ブラックボックステスト** — 中身を見ずに、仕様（入力と期待される出力）からテストを作ります。QAのテストの多くはこちらです。
- **ホワイトボックステスト** — コードの分岐や処理の流れを見て、すべての経路を通るようにテストを作ります。主に単体テストで使います。

ホワイトボックステストでは、コードのどれだけを実行したかを **カバレッジ** で測ります。

- **命令網羅（C0）** — すべての行を1回以上実行したか。
- **分岐網羅（C1）** — すべての `if` の真と偽を両方とも通ったか。

カバレッジは「テストしていない場所」を見つける道具です。100%でも、期待結果の確認（アサーション）が甘ければ不具合は見逃されます。数字を目的にしないよう注意しましょう。

## テスト設計技法

「どんなテストケースを作るか」を、勘ではなく根拠をもって決めるための方法です。少ないケースで効率よく不具合を見つけられます。
ここでは、年齢入力欄（18〜65歳のみ登録可、整数のみ）を例に説明します。

### 同値分割

同じ扱いになる入力をグループ（同値クラス）に分け、各グループから代表値を1つ選びます。

| グループ | 種類 | 代表値 |
|---|---|---|
| 17以下 | 無効 | 10 |
| 18〜65 | 有効 | 30 |
| 66以上 | 無効 | 80 |
| 数字以外 | 無効 | `abc` |
| 空欄 | 無効 | （未入力） |

### 境界値分析

不具合は「以上・未満」の取り違えなど、**境目**に集中します。境界とその両隣の値をテストします。
例：17、18、65、66。余裕があれば 19 や 64 も加えます。
同値分割と境界値分析はセットで使うのが基本です。

### デシジョンテーブル

複数の条件の組み合わせで結果が変わるときに、表で整理して漏れを防ぎます。
例：送料無料の条件が「会員である」かつ「購入金額が5,000円以上」の場合。

| 条件・結果 | ケース1 | ケース2 | ケース3 | ケース4 |
|---|---|---|---|---|
| 会員である | Y | Y | N | N |
| 5,000円以上 | Y | N | Y | N |
| **送料無料** | **〇** | × | × | × |

### 状態遷移テスト

画面やデータの「状態」と、状態が変わるきっかけ（イベント）を図や表にして、遷移を確認します。
例：注文の状態「未決済 → 決済済み → 発送済み → 完了」。正しい遷移だけでなく、「発送済みの注文をキャンセルできてしまわないか」のような **ありえない遷移** も確認するのがポイントです。

### ペアワイズ法（オールペア法）

組み合わせが多すぎて全部試せないときに、**任意の2つの項目の組み合わせ** がすべて1回は出るようにケースを減らす方法です。
例：OS 3種 × 画面サイズ 3種 × 言語 3種 = 27通りを、約9通りまで減らせます。多くの不具合は2つの要素の組み合わせで起きる、という経験則に基づいています。専用ツールで組み合わせを作るのが一般的です。

### エラー推測

経験や過去の不具合から「ここは壊れやすそう」という箇所を狙ってテストします。
例：0件・1件・大量件数、絵文字や改行を含む文字列、同じボタンの連打、通信の途中切断。
体系的な技法と組み合わせると効果的です。

## 手動テストと自動テスト

どちらかが優れているのではなく、得意なことが違います。

| 観点 | 手動テスト | 自動テスト |
|---|---|---|
| 得意なこと | 見た目・使い心地の確認、仕様が固まっていない機能、探索的な確認 | 同じ確認の繰り返し、大量の組み合わせ、夜間やCIでの実行 |
| 初期コスト | 低い | 高い（テストコードの作成が必要） |
| 繰り返しのコスト | 毎回かかる | ほぼかからない |
| 苦手なこと | 繰り返しによる疲れ・見落とし | 想定外の問題への気づき、頻繁な画面変更への追従 |

### 自動化に向いているテスト

- 何度も繰り返すリグレッションテストやスモークテスト
- 仕様が安定していて、結果を機械的に判定できるもの
- 手作業ではミスしやすい大量データや計算の確認

### 自動テストで気をつけること

- **フレーキーテスト** — コードを変えていないのに、成功したり失敗したりするテストです。待ち時間の不足や、テスト同士のデータの干渉が主な原因です。放置すると「どうせまた失敗」と結果が信用されなくなるため、早めに直します。
- **保守コスト** — 画面が変わるたびにテストの修正が必要です。画面操作のテストは重要な流れに絞りましょう。
- **期待結果の確認** — 操作するだけで結果を確認しない自動テストは、何も保証しません。

Androidアプリの場合、単体テストには JUnit、画面操作の自動化には Espresso・UI Automator・Maestro・Appium などがよく使われます。

## 探索的テスト

あらかじめテストケースを用意せず、**アプリを触りながら学び、次に試すことをその場で考える** テスト手法です。テストケースに書かれていない不具合を見つけるのに向いています。

進め方の例：

1. **チャーター（目的）を決める** — 例：「通信が不安定なときの投稿機能を探索し、データ消失のリスクを探る」
2. **時間を区切る** — 60〜90分程度のセッションにします。
3. **気づいたことを記録する** — 試したこと、見つけた不具合、疑問点をメモします。
4. **振り返る** — 見つけた問題をチームに共有し、必要なら新しいテストケースにします。

「適当に触る」こととは違い、目的と記録があるのが探索的テストです。

## テストケースの書き方

良いテストケースは、**誰が実施しても同じ結果を判定できる** ものです。このポータルのテスト項目の各欄も、この考え方に沿っています。

| 欄 | 書き方のポイント | 例 |
|---|---|---|
| 識別子 | 機能ごとに規則的に付ける | `LOGIN-003` |
| テスト項目名 | 何を確かめるかを一文で | 誤ったパスワードでログインするとエラーが表示される |
| 事前条件 | テスト開始時の状態を具体的に | 登録済みユーザー `test01` が存在し、ログアウトしている |
| 手順 | 1行に1操作。曖昧な言葉を避ける | ログイン画面でメールに `test01@example.com` を入力する |
| 期待結果 | 合否を判定できる具体的な結果 | 「パスワードが違います」と表示され、ログイン画面に留まる |

### よくある失敗

- **期待結果が曖昧** — 「正しく動作すること」では判定できません。何が表示され、何が保存されるかを書きます。
- **1ケースに確認が多すぎる** — 失敗したときに、どこが悪いのかわからなくなります。1ケース1目的が基本です。
- **正常系しかない** — 誤入力、通信エラー、権限なしなどの **異常系** こそ不具合が見つかりやすい場所です。
- **ケース同士が依存している** — 前のケースの結果を前提にすると、1つの失敗が連鎖します。事前条件で状態を明示しましょう。

## Androidアプリで確認したい観点

モバイルアプリには、Webや業務システムとは違う特有の観点があります。テストケースを作るときのチェックリストとして使ってください。

- **端末とOS** — Androidのバージョン、メーカー独自の挙動、画面サイズや解像度、タブレットや折りたたみ端末
- **画面の回転と構成の変更** — 回転、ダークモード切り替え、言語変更の後も、入力内容や表示が保たれるか
- **ライフサイクル** — バックグラウンドに回して戻る、OSにアプリを終了させられた後に再開する
- **割り込み** — 電話の着信、通知、アラーム、他アプリへの切り替え
- **ネットワーク** — 圏外、機内モード、Wi-Fiとモバイル回線の切り替え、遅い回線
- **権限** — カメラや位置情報などの権限を「許可しない」、後から設定で取り消す
- **端末の状態** — 電池残量が少ない、省電力モード、ストレージ不足
- **表示と操作** — 文字サイズを最大にする、TalkBack（読み上げ）で操作する、戻るボタンやジェスチャーナビゲーション
- **インストールと更新** — 新規インストールと、旧バージョンからのアップデートの両方でデータが正しく引き継がれるか

## テストの進め方

テストは、実行するだけの作業ではありません。一般的には次の流れで進めます。

1. **テスト計画** — 目的、範囲（やること・やらないこと）、スケジュール、体制、終了条件を決めます。
2. **テスト分析** — 仕様書やユーザーストーリーから「何をテストするか」（テスト観点）を洗い出します。
3. **テスト設計** — 設計技法を使い、「どうテストするか」を具体的なケースにします。
4. **テスト実装** — テストデータや環境、自動テストのコードを準備します。
5. **テスト実行** — テストを実施して結果を記録します。このポータルの「テスト実行」はこの段階を記録するためのものです。
6. **テスト完了** — 結果をまとめ、終了条件を満たしたか、残ったリスクは何かを報告して振り返ります。

### 終了条件の例

- 優先度「高」のテストケースがすべて成功している
- 重大度「致命的」「重大」の未解決不具合がない
- 未解決の不具合は、関係者がリスクを理解したうえでリリースを了承している

## 不具合の報告

不具合を見つけたら、開発者が **再現でき、すぐ原因調査に入れる** ように報告します。

### 報告に含める内容

- **タイトル** — 何が、どうなるかを短く。例：「プロフィール編集で絵文字を保存するとアプリが落ちる」
- **環境** — アプリのバージョン、端末名、Androidのバージョン、通信状態
- **再現手順** — 誰でも同じ操作ができるように、番号付きで書く
- **期待結果と実際の結果** — 本来どうなるべきで、実際にはどうなったか
- **再現頻度** — 毎回か、10回中2回か
- **証跡** — スクリーンショット、画面録画、ログ

### 重大度と優先度

似た言葉ですが、意味が違います。

- **重大度（Severity）** — 不具合が与える影響の大きさ。例：データが消える、アプリが落ちる、表示が少しずれる。
- **優先度（Priority）** — どの順番で直すか。ビジネス上の都合も含めて決めます。

例えば「トップ画面の会社名の誤字」は重大度は低くても、目立つので優先度は高くなることがあります。反対に、ほとんど使われない設定画面でのクラッシュは、重大度は高くても後回しにされる場合があります。

## QAエンジニアとは

QA は Quality Assurance（品質保証）の略です。QAエンジニアは、**ソフトウェアの品質を、開発の最初から最後まで支える役割** を担います。

### テスターとの違い

- **テスター** — 主に、用意されたテストを実行して結果を報告します。
- **QAエンジニア** — テストの実行に加えて、テスト計画・設計、品質の基準作り、開発プロセスの改善までを担います。「不具合を見つける」だけでなく「不具合を作り込まない仕組みを作る」ことも仕事です。

### 主な仕事

- 要件や仕様のレビューに参加し、曖昧な点やテストしにくい点を早期に指摘する
- テスト計画を立て、リスクに応じてテストの範囲と優先度を決める
- テストケースを設計し、手動テストや探索的テストを実施する
- 自動テストを作り、CI（継続的インテグレーション）に組み込む
- 不具合を報告し、修正の確認とリグレッションテストを行う
- 不具合の傾向やテスト結果を分析し、チームに改善を提案する
- リリース判定のための品質情報をまとめる

### 求められるスキル

| 分野 | 内容 |
|---|---|
| テスト技術 | テスト設計技法、テストプロセス、探索的テスト |
| 技術力 | プログラミング、テスト自動化ツール、API・DB・ネットワークの基礎、CI/CD |
| ドメイン知識 | 対象の業務や利用者の使い方への理解 |
| コミュニケーション | 不具合を事実ベースで伝える力、開発者・PO・デザイナーとの調整力 |
| 分析力 | リスクを見極め、限られた時間で何をテストするかを判断する力 |

### キャリアの広がり

テスト自動化を専門にする **SET（Software Engineer in Test）**、品質の仕組みをチーム全体で整える **QAリード・品質マネージャー**、テスト戦略を組織横断で担う **テストアーキテクト** など、経験に応じてさまざまな道があります。

## テストの結果を読む

数字はチームの状況を知る手がかりになりますが、数字だけで品質は判断できません。

- **成功率** — 成功したケースの割合。ただし、簡単なケースばかりなら高くて当然です。何をテストしたかとセットで見ます。
- **未実施の数** — 残っている作業量です。リリース直前に多ければ、範囲の見直しが必要です。
- **失敗・保留の推移** — 回を重ねても減らない機能は、設計や実装に根本的な問題があるかもしれません。
- **不具合の偏り** — 特定の画面や機能に不具合が集中していれば、その周辺のテストを厚くします（「欠陥は偏在する」原則）。

このポータルのテスト一覧では、直近2回の結果を並べて比べられます。前回は成功していたのに今回失敗した項目は、リグレッション（デグレード）の可能性が高いので、最優先で確認しましょう。

## 用語集

| 用語 | 意味 |
|---|---|
| テストケース | 事前条件・手順・期待結果をまとめた、1つの確認単位 |
| テストスイート | 目的ごとにまとめたテストケースの集まり |
| 正常系・異常系 | 想定どおりの操作・入力と、誤りや例外的な操作・入力 |
| デグレード（デグレ） | 修正によって、以前は動いていた機能が壊れること |
| リグレッションテスト | デグレが起きていないかを確かめるテスト |
| フレーキーテスト | 同じ条件でも結果が安定しない自動テスト |
| カバレッジ | テストで実行・確認できた範囲の割合 |
| モック・スタブ | テストのために本物の代わりに使う、偽の部品 |
| CI | コードの変更のたびに、ビルドとテストを自動で実行する仕組み |
| シフトレフト | テストや品質の活動を、開発の早い段階に前倒しする考え方 |
| E2Eテスト | 利用者の操作を最初から最後まで通して確認するテスト |
| TDD | テスト駆動開発。先にテストを書き、それを通すようにコードを書く開発手法 |

## さらに学ぶには

- **JSTQB Foundation Level** — ソフトウェアテストの国際資格の入門レベルです。シラバス（学習範囲）は公式サイトで公開されており、用語や考え方を体系的に学べます。
- **書籍** — 『知識ゼロから学ぶソフトウェアテスト』（高橋寿一）はテストの全体像をつかむ入門書として定番です。テストを開発に組み込む考え方は、『テスト駆動開発』（Kent Beck）が参考になります。
- **実践** — まずは身近なアプリで、同値分割と境界値分析を使ってテストケースを10件書いてみましょう。書いたケースはこのポータルに登録して、実行と振り返りまで回してみるのがおすすめです。
